### 2.2 Modifications to Existing Tables

- **`invoices` table**: Already has `items` JSON column storing line items. The existing item structure likely includes `product_id`, `name`, `quantity`, `price`, etc. We'll need to ensure it stores the **invoice quantity** (in the product’s sale unit, e.g., "3 Shirts" or "5 Meter") and the **deducted stock** (`consumed_stock`).  
  Add a nullable `product_id` column if not already present in the items JSON.  
  A new column `stock_deduction_type` may be added to the invoice itself, but it's better to pull it from the product per line item.  

- **`invoice_items` table** (if separate table exists; spec earlier used JSON but might have a dedicated table). For robust relational queries, a dedicated `invoice_items` table is preferable. However, the existing code uses JSON. We'll need to be consistent.  

Given the importance of stock deduction tracking, I recommend moving invoice items to a **relational `invoice_items` table** (migration: `id, invoice_id, product_id, product_name, quantity, unit, price, discount, tax_details, consumed_stock, stock_deduction_type`). This will make stock history lookups and adjustments far easier.

- **`companies` table**: No direct change, but stock is company‑scoped.

## 5. Architecture Decisions & Recommendations

### 5.1 Stock Deduction Type Flexibility

Adopt the user’s suggestion and store `stock_deduction_type` as a string with allowed values: `Meter`, `Piece`, `Kg`, `Roll`, `Box`, `Custom`.

- In `StockService`, a strategy pattern or simple `match` will handle deduction logic:
  - `Meter`, `Kg`, etc.: quantity directly deducted from stock (1 invoice unit = 1 stock unit).
  - `Piece`, `Roll`, etc.: requires `consumption_per_piece` field; deduction = `quantity × consumption_per_piece`.
  - `Custom`: could support a formula or manual entry.

### 5.2 Stock as a Single Decimal Column

All stock is stored in a base unit (e.g., Meter, Kg). The `stock_unit` column is for display only. This simplifies calculations. If a company uses multiple units (e.g., some products in Kg, some in Meters), that’s fine; calculations remain correct because we never convert across units.

### 5.3 Invoice Items Relationship

Existing system stores invoice items as JSON in an `items` column. While we can keep that, stock tracking becomes fragile because we’d need to parse JSON every time to fetch consumed stock. Migrating to a dedicated `invoice_items` table is strongly advised. It also enables proper reporting queries.

**Migration path:**

1. Create `invoice_items` table.
2. Run a one‑time seeder/command to migrate existing JSON items into the new table.
3. Update all invoice services and repositories to use the relational model.
4. Keep the old JSON column for backward compatibility until fully transitioned.

Given the multi‑phase nature of your project, this migration is a separate mini‑project but crucial for clean stock handling.

### 5.4 Transaction Management

Any operation affecting stock (invoice create/edit/delete, manual adjustment) must be wrapped in a database transaction with appropriate locks to prevent race conditions. In Laravel, use `DB::transaction()` and consider `lockForUpdate()` on the product row when deducting stock.

## 6. Potential Risks & Mitigation

| Risk | Mitigation |
|------|------------|
| Stock inconsistency due to partial failures | Wrap invoice + stock operations in DB transactions. Rollback on failure. |
| Concurrent stock updates | Use pessimistic row locking (`lockForUpdate()`) during deduction. |
| Large CSV imports cause timeouts | Use Laravel queue jobs for processing imports; background job with progress updates. |
| Changing invoice items table breaks existing functionality | Implement migration as a separate release with thorough testing and fallback. |
| Complex consumption logic for future types | Use a factory or strategy pattern in `StockDeductionCalculator` to encapsulate per‑type logic. |
